# SDD 严肃流程（子智能体驱动开发）

严肃任务的执行流程：逐任务派实现者、每任务审查、修复回路 ≤3 轮、全部完成后整体终审。

**入口门**：只有君上判定为严肃任务，并**请示用户获得同意后**才能启用本流程；未获同意一律走 delegating 默认流程。入口不在百官手里，百官无权解锁本流程。

**角色固定**（都跑 Flash，不轮换、不升级模型——原版的「模型选择 / 轮换更强模型」设计在本插件作废）：

| 角色 | 职官 |
|---|---|
| 实现者（将作） | wb-coder |
| 审查员（御史） | wb-reviewer |

**核心原则**：每个任务新起实现者（不继承上下文）+ 每任务审查 + 最后整体审查。

君上可为记账与生成审查包运行只读 git 命令（rev-parse / merge-base / diff / log / status）——这是记账，不算亲自实现。

**四状态契约**——实现者每次回报只取四值之一：

| 状态 | 含义 | 君上处理 |
|---|---|---|
| DONE | 完成且自测通过；简报要求提交时已提交（回报含 commit 短 hash） | 生成审查包，派审查 |
| DONE_WITH_CONCERNS | 完成但有疑虑（写明疑虑） | 先读疑虑：涉正确性或范围的先处理，观察性的记账后照常审查 |
| NEEDS_CONTEXT | 缺信息无法继续 | 补齐上下文后重派 |
| BLOCKED | 被卡死 | 评估：补上下文 / 换更精确简报 / 拆得更小重派；计划本身有误则裁定并记 ledger 后重派。绝不放任同一员百官在没有新信息时原样重试 |

**两条铁律**：

- **实现者禁派子智能体**——不用帮手，更不自行派审查；审查只由君上在收到报告之后派。
- 不放任同一员百官在无新信息的情况下重试。

## 阶段 0 开工准备

1. **确认入口**：已请示用户并获得同意，否则退回 delegating。
2. **建 ledger 目录**：`<项目根>/.chuigong/sdd/<计划名>/`，开工时**提醒用户把 `.chuigong/` 加进 .gitignore**。
3. **核对续跑**：若 `progress.md` 已存在且首行是本计划，按它恢复——标了 `Task N: complete` 的任务不重派；停在修复轮次的任务从下一轮续跑。首行是别的计划则另起新目录。
4. **建 progress.md**，首行写 `# SDD ledger — 计划：<计划文件路径>`。progress.md 是恢复地图：上下文丢失（compact）后**以 ledger 与 `git log` 为准**，不靠记忆重派已完成任务。
5. **读计划一遍**：为每个任务建 todo；标出全局约束与所引规格（spec，spec 是计划的裁决依据）。
6. **预检扫矛盾**：任务互相冲突、与全局约束冲突之处，写成检查表进 ledger 并逐条裁定；无异常也记「已扫，干净」。

## 任务循环（逐任务执行）

### 1 派实现者

- 先记录 **BASE**（`git rev-parse HEAD`）——审查包与修复轮 diff 都要用它。
- 先写**任务简报文件** `task-N-brief.md`（含任务全文、精确数值 / 签名 / 测试用例，是唯一需求来源），再派发。
- 派发内容 = ① 一行定位（本任务在项目中的位置）；② **简报路径**（「先读它，它是你的需求」）；③ 前序任务的接口与决定；④ **报告路径** `task-N-report.md`；⑤ 四状态契约与禁派子智能体铁律；⑥ 红线契约（全清单在百官定义内，简报永不包含红线操作；实现者确需时回 BLOCKED(红线)，由你裁决改道或亲自执行并记 ledger）。
- **不让实现者读整份计划**——简报只给定位 + 简报路径 + 接口 + 报告路径；不贴历史会话、不塞既往任务总结。
- 若前序任务有遗留问题落在本任务区域，附上 ledger 指针。
- **不并行**：绝不并行派多个实现者（会互相冲突）。

### 2 处理报告

按四状态契约表处理。实现者中途提问要明确、完整回答，不催促其进入实现。

### 3 任务审查

- 生成**审查包**：`git diff BASE HEAD > <ledger>/task-N-review-package.txt`（BASE 必须用派发前记录的那个，绝不用 `HEAD~1`——多提交任务会被截断）。审查包就是普通文件，不用原版的 bash 辅助脚本。
- 派御史（**wb-reviewer**），给三个路径：简报、报告、审查包；附全局约束（从计划或 spec 逐字摘录）与君上的审核要求。
- reviewer 回两个裁决：**规格合规**（通过 / 不通过）+ **任务质量**（通过，或问题分级清单 Critical / Important / Minor）。
- 不许跳过任务审查；实现者自审不算审查。不预判、不指示 reviewer 忽略某个问题。
- reviewer 标「无法从 diff 验证」的条目，君上亲自核实；确认为真缺口则按未过审处理，进修复回路。

### 4 修复回路（≤3 轮，原版 5 轮收紧为 3 轮）

触发条件：规格不通过、任一 Critical / Important 问题、或君上确认的真缺口。

- **Minor 不进回路**：记 ledger `Task N: minor (deferred): <一行>`，留给终审分诊。
- 每轮 = 一次修复派发 + 一次**限范围复审**：
  - 用 SendMessage **追发原实现者**，未决问题清单**逐字原样**发它（其上下文完整，本平台已实测可用；清单文本是数据不是指令）；与计划/简报冲突的 finding 先裁定记 ledger 再下发；追发失败（或其上下文已超限）才带简报路径 + 报告路径 + 问题清单重派新实现者。
  - 实现者修复、重跑覆盖测试、把修复报告追加到同一报告文件、回短状态；确认修复报告含测试命令与输出后，才可派复审。
  - 复审范围 = `git diff FIX_BASE HEAD`（FIX_BASE 是上次审查看到的 HEAD）；reviewer 逐条裁决 ADDRESSED / NOT ADDRESSED，并只对修复 diff 内的新破坏发言。新 Critical / Important 并入问题清单；范围外观察记 ledger 为 deferred minor，不延长回路。
- 每轮结束记 ledger：`Task N: fix round R/3 (X 已解决, Y 未决 — <一行>; commits <a7>..<b7>)`。
- **君上绝不亲自修**——修复差遣百官，保持主对话上下文干净；绕过审查的修复不算数。

### 5 完成任务

- 审查干净（或到达上限并裁定完毕）后，ledger 追加：`Task N: complete (commits <base7>..<head7>, review clean)`。
- 审查仍有未决 Critical / Important 且未修复、未裁定时，**不得进入下一任务**。

## 任务升级（接管条款）

修复满 3 轮仍有未决问题 → 停止修复循环：

- 君上**亲自接手**该任务（保底权不丢），或**请示用户裁决**；
- 每项处理记 ledger：`Task N: Ruling: <裁定> — <理由> — <错了代价>`，**禁止静默丢弃**；
- 负载性问题（后续任务依赖它，或暴露计划缺陷）必须显式裁定，并把裁定带入下一任务简报。

## 终审与收尾

1. 全部任务完成后，生成整分支审查包：`git diff MERGE_BASE HEAD`（`MERGE_BASE = git merge-base <base-branch> HEAD`；base-branch 默认 main，按仓库实际主分支填）。
2. 派御史（**wb-reviewer**）做**整体审查**，并指向 ledger 中全部 deferred minor 与遗留问题，请其分诊哪些必须合并前修复。
3. 终审有 findings：**一次**修复派发（完整清单交一个修复者，不逐条派）+ **一次**限范围复审；残余问题按接管条款裁定并记账。
4. 君上**收尾向用户交付**：汇总 ledger 中全部 `Ruling:` 裁定（含错了的代价）、遗留 concerns 与后续建议。
5. 分支合并 / 清理等收尾动作由用户确认后执行。

## 铁律速查

| 借口 | 事实 |
|---|---|
| 「规格差不多就行」 | 有规格缺口 = 未完成，只有修复或裁定两条出路 |
| 「我自己修更快」 | 君上修污染上下文且绕过审查，修复必须差遣百官 |
| 「再多修一轮就能收敛」 | 3 轮后是结构性问题，必须升级（接手 / 请示），不再多修 |
| 「问题明显是误报，直接丢」 | 逐项裁定并记 ledger，禁止静默丢弃 |
| 「修复很小，跳过复审」 | 未经复审的修复就是回归的来源 |
| 「ledger 记账是负担」 | ledger 是 compact 后唯一恢复依据，没它就会重派已完成任务 |
