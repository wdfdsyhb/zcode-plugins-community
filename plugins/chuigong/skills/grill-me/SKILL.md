# 究诘（需求拷问）

把含糊的需求拷问清楚再动手。追问者＝**君上本体（主对话）**——子智能体没有向用户提问的通道（平台约束），只能代查事实。

## 入口与硬闸门

- 进入条件（二选一）：用户显式开启（/grill-me 或明说）；主对话提议「建议先究诘」且用户同意。**绝不未经同意自动开始拷问。**
- 硬闸门：究诘期间不写代码、不差遣执行类百官开工、不产出任何实现物；唯一的文件产出是需求纪要。
- 需求已精确到可执行时，明说「无需究诘」，回 delegating 正常流程。

## 开始前

1. **先查后问**：代码库/环境里能查到的事实，派通政 wb-researcher（后台）代查，把「能查到的」从问题清单里删掉；等结果期间先问不依赖它的问题，不阻塞。
2. **开场声明拷问计划**：大约几轮、聚焦什么、什么算问完——让用户可随时叫停或缩范围。

## 追问法（决策树 ＋ 前沿）

- 把需求建模为**决策树**：每个决策分出挂在它下面的后续决策；**前沿**＝前置决策都已落定的那些问题，只问前沿。
- **一轮问整条前沿**：用 AskUserQuestion 一次 ≤4 问；每问 2-4 个具体选项、**推荐项放第一位**；需要长段自由回答的开放问题才改为普通文本一次一问。
- 每轮结束：复述本轮已决项 → 重算前沿 → 开下一轮。计数按轮不按问（4 轮 40＋问属正常），但要盯失控信号。
- 顺序参考：① 基础（一句话目标 / 触发时机 / 范围与非目标 / 成功判据）→ ② 形态（输入输出 / 关键约束 / 依赖与集成）→ ③ 边界与对抗（极端与失败模式 / 隐含假设 / 与已答内容的矛盾）。
- **防膨胀**：问题突然变多＝预警，先自查是否越界；超过 6 轮前沿仍大 → 提议**拆分需求**（减范围 / 拆多次会话），不是继续堆问题；用户答「都行 / 随便」→ 用带推荐项的追问逼实。
- **不可拷问项**：需要「看到东西才能答」的（视觉 / 手感 / A/B）→ 停该分支，提议先做一次性原型再回来定夺。

## 停止（三条同时满足才停）

1. 前沿为空：没有默默假设的决策；
2. 无悬空依赖：未决项已显式记入「延期清单」；
3. 用户显式确认达成共识（主对话不得代用户宣布）。

## 产出：需求纪要

君上亲写（问答全在你上下文里，无需差遣百官）到 `.chuigong/grill-me/<YYYY-MM-DD>-<主题>.md`：

```
# 需求纪要：<标题>
- 日期：YYYY-MM-DD ｜ 原始需求：<用户最初表述原文>

## 1 一句话目标
## 2 范围与非目标（明确不做的事）
## 3 已决决策（表：# / 决策 / 理由 / 曾考虑的备选）
## 4 延期与未决项（附重新决策的触发条件）
## 5 未验证假设
## 6 风险与不可逆点
## 7 成功判据与验收方式
## 8 建议下一步（拆解草案；疑似严肃任务提示走 sdd 请示）
```

## 交棒

纪要获用户确认后究诘结束 → 按 delegating 拆解派发（简报的目标 / 边界直接摘自纪要，纪要即简报的事实来源）；命中严肃任务条件（多文件改动 / 高风险 / 不可逆）→ 先走 sdd 请示。**究诘本身不构成执行许可。**
