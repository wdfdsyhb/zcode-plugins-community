# Theory Refine Loop · 理论分析迭代修正环

本 skill 是 `math-proof-reviewer` 的编排层：**审查交给 reviewer，修改由你自己执行**。你负责送审、按意见改稿、记录台账、判定循环何时终止。依赖 math-proof-reviewer 可用（本机 ZCode 与 opencode 均已安装）。

总流程：准备 → 送审 → 判定 →（可修复：修改 → 再送审）→ 通过 ｜ 判死 → 输出。

## 第 0 步：准备（只做一次）

1. 确定送审材料：`.tex` 直接 Read（优先，可精确定位行号）；`.md` / 纯文本直接读；PDF 用 Read 工具；`.docx` 先用 docx 工具链转文本。材料含 `\input` / `\include` 时把整个文件集纳入。
2. 一次性向用户确认三件事（合并成一组问题，不要反复打断）：**审查范围**（全部证明还是指定定理/标签）、**数学领域**（reviewer 需要它确定审查重点）、**定理来源**（原创还是文献引用）。之后送审时把这三项随材料一并声明"已确认"，避免 reviewer 的阶段 0 再次提问。
3. **原文件永远不动**：复制一份工作副本 `<原名>_revised.<扩展名>`（多文件时复制整个目录），后续所有修改只发生在副本上。
4. 建立审查台账（在回复中维护即可）：每轮记录 轮次 k ／ ⚠️ 问题数 ／ 修改清单（问题 → 改了哪里）／ 审查结论。每轮修改前把当前副本快照为 `<原名>_revised_r<k>.<扩展名>`。

## 第 1 步：送审

- 第一轮：通过 Skill 工具加载 `math-proof-reviewer`（opencode 中为 skill 工具），把工作副本与已确认的领域/范围/来源一起交给它，要求按其五段结构输出报告。
- 后续轮次：reviewer 的指引已在上下文中时**不要重复加载**，直接按其四维度标准（前提充分性、引理使用、逻辑链条、边界与反例）对**新副本**重新审查，报告格式不变。
- 每轮送审对象必须是修改后的新副本，并附上"上一轮改了什么"的修改清单，便于 reviewer 逐条复核。

## 第 2 步：判定（每轮审查后）

读报告的「一、整体结论摘要」、分步审查表中的 ⚠️ 项与「四、存疑清单」：

- **无 ⚠️ 且摘要判定证明成立** → 走第 4 步通过路径。
- **有 ⚠️ → 先分性质，再动手：**
  - **可修复问题**（改写证明即可消除）：推导笔误、不等式方向写反、量词顺序错误、漏验证前提、引理条件不满足但可补论证、边界情况遗漏、记号错误、引用编号错配等 → 走第 3 步。
  - **根本性问题**（改写证明救不了）：reviewer 构造的反例成立、定理本身为假、结论在给定假设下本质推不出（缺的条件是实质性的，不是补一句话能补的）、必须削弱定理陈述才能证 → 停止循环，直接走第 5 步失败报告，并向用户说明为什么不再继续改。
- **存疑 ≠ 问题**：存疑只是信息不足。能通过查引用原文、补推导消除的存疑先消除；卡在关键步骤无法消除的，按问题计入并向用户说明缺什么。

## 第 3 步：按意见修改

1. 逐条对照审查意见修改工作副本。reviewer 只指出缺口不代写，**补全论证是你的责任**——补写的推导必须先自己按四维度标准过一遍，再提交送审。
2. 只动理论相关内容，保持 LaTeX 可编译、定理/公式编号体系不被破坏；多文件项目同步修改被 `\input` 的文件。
3. **禁止为了让循环通过而悄悄弱化定理陈述、删除或放松假设**——凡需要改动"结论本身"的修改，一律停下转第 5 步，说明为什么必须弱化、给出候选弱化方案，由用户决策。
4. 台账记录每条问题对应的修改位置；快照为 r<k> 后回到第 1 步。

### 循环终止规则

- **上限 5 轮**：达到上限仍有未消除的问题 → 停止，转第 5 步失败报告，说明已达轮次上限并列出顽固问题。
- **顽固问题**：同一问题连续两轮未消除即标记；顽固问题数量不再下降 → 停止，转第 5 步。
- 每轮结束用一两句话向用户报告进展：第几轮、消除了几个问题、还剩几个。

## 第 4 步：通过路径（没问题）

最终回复必须包含：

1. 明确写出「**没问题**」；
2. reviewer 最终轮的确认要点（哪些定理/证明被判成立）；
3. 修改清单汇总（轮次 → 问题 → 修改位置），让用户清楚改了什么；
4. 工作副本路径；删除中间快照只留终稿（用户要历史版本时除外）。

## 第 5 步：失败报告（理论过不去）

输出**详细原因说明**，五项缺一不可：

1. **判死结论**：明确指出哪个定理/引理站不住，一句话结论。
2. **具体原因**：引用 reviewer 报告原文——反例要完整给出（具体函数/数列/数值，并指出它在哪一步失效）；逻辑断层要指出差哪一步、缺什么条件；引理为假要指出错在何处。
3. **每轮记录**：第 1–k 轮各发现什么、改了什么、为什么没救回来。
4. **可能的出路**（供用户决策，不是替用户决定）：结论可以削弱到什么程度仍可证、需要补什么假设、可换什么证明策略；明确警告这些改动会改变结果本身。
5. **文件清单**：原文件（未动）、各轮快照、最终失败版本，列明路径。

## 红线

1. 原文件永远不动，所有修改在工作副本上。
2. 每轮必须真的把新副本送审，不许凭记忆或自我感觉宣布「应该没问题了」。
3. 不许靠弱化命题换取通过；要弱化就停下请用户决策。
4. 判定「理论过不去」必须引用 reviewer 的具体依据（反例／断层／假引理），不许凭感觉判死。
5. 通过就说「没问题」并给依据；失败就给详细原因。不许含糊其辞，也不许中途撒手不管。
