# 模式二：功能分析（点击式学习模式）

触发："分析登录功能"、"分析 XX 功能/接口/模块"、"讲讲这个接口"。

## 核心规则

1. **不重新全量扫描。** 直接按关键词定位：
   - `Grep: 关键词`——中文注释、拼音、英文命名都试（如"登录"/"login"/"auth"）
   - 定位到接口后，只沿调用链读取相关文件。
   - 若此前已做过全量分析，直接复用已生成的看板数据与扫描结论，缺什么补什么。
2. **分析对象必须真实存在。** 找不到相关代码时，**在对话里如实说"项目中未找到与 XX 相关的代码"**，列出最接近的候选（附证据），请用户确认后再继续——不许挑一个无关接口硬讲，更不许虚构一个登录功能。
3. 全程遵守 `references/evidence-rules.md`；数据结构见 `references/dashboard-data.md`。

## 输出：单页功能看板

用同一模板生成 `docs/feature-{功能名}.html`（cp + Edit 替换 DATA 占位，流程同 SKILL.md 输出约定）：

- `meta.project` 填"功能名 · 所属项目"
- 只填与该功能相关的部分：`modules`（一个模块，含该功能的接口与完整 detail 十节）、`techs`（该功能真实用到的组件）、`flows`（该功能的数据流）、`terms`（该功能涉及的术语）
- 其余字段省略或留空数组，渲染器显示空状态
- 若全量看板已存在，在对话里说明：功能看板是深钻视图，全貌以 `architecture-analysis.html` 为准

## 13 步固定结构（对应 detail 十节 + 对话补充）

对选定的功能，按以下顺序分析。某一步在该功能中确实不存在时，明确写"本功能调用链未涉及 XX"并给出判断依据，不许默默跳过：

① **业务目的** —— 从入参出参与命名可确认的直说；推断的标【推测】。
② **涉及接口** —— HTTP 方法 + 完整路径 + Controller 方法签名。
③ **Controller** —— 类/方法、注解、参数校验方式（附文件路径）。
④ **Service** —— 业务逻辑逐步讲：判断、调用、事务注解、异常。
⑤ **数据访问** —— Mapper/Repository 方法；SQL 来自注解、XML 还是框架内置【框架行为】。
⑥ **数据库** —— 表、关键字段（从 @TableName/@Table、实体字段、SQL 确认）。
⑦ **Redis** —— 调用链中有没有？有：按判定树判断用途；无：写明"本功能调用链未发现 Redis 调用"。
⑧ **Sa-Token / MQ / AI / 其他组件** —— 有就讲在本功能里干了什么；没有就写明。不许把无关组件硬拉进来。
⑨ **完整调用链** —— detail.chain 文本链（真实类名.方法名）。
⑩ **数据流** —— flows.shapes：每一步数据长什么样、放在哪个对象里。
⑪ **为什么这样设计** —— 写进 detail 与 flows.points；必须结合本项目真实代码，不许背八股范文。
⑫ **学渣版解释** —— techs[].xuezha 与 terms；比喻基于本项目真实结构。
⑬ **面试题** —— 在对话里给 3-5 道（题目与答案来自本功能真实代码，规则同 interview-mode.md），并可直接填入功能看板的 `DATA.interview`。

## "继续" = 向下深挖一层

用户说"继续"时，挑当前链条上最有学习价值的环节向下钻（对话中输出，或按用户要求更新看板）：

- Service 某个方法的内部逻辑逐段讲
- SQL 细节、条件拼接与索引分析
- 涉及的框架机制——讲框架机制时明确标注"以下是框架源码/机制，不是本项目代码"
- 自定义异常是谁捕获、如何转成响应

每一层依然遵守证据规则。
