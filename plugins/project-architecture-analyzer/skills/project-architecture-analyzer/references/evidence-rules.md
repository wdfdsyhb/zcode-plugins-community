# 证据分级规则（第一原则详细版）

## 为什么需要这条规则

逆向分析最大的风险是"脑补"：模型见过大量 Spring Boot 项目，很容易用"常见套路"填补没读到的部分。对学习者来说，一条虚构的调用链比没有分析更有害——他会带着错误理解去面试。本 skill 的可信度完全建立在"每个结论有代码证据"上，宁可文档短一点，不可结论假一句。

## 证据四级标记

| 标记 | 含义 | 使用条件 |
|---|---|---|
| 【已确认】 | 代码中直接存在 | 必须能给出文件路径，必要时给类名/方法名 |
| 【推测】 | 基于代码的合理推断 | 必须同时写出推断依据 |
| 【框架行为】 | 框架自动配置/内置机制完成的行为，非业务代码 | 必须说明是哪个框架的什么机制 |
| 【待确认】 | 无法从当前扫描确定 | 必须同时给出"去哪里确认"的线索 |

判断口诀：**写出来的才算【已确认】，推出来的要标【推测】，框架干的标【框架行为】，猜出来的不允许存在。**

## 六条严禁

1. **严禁根据常见 Spring Boot 项目套路猜测不存在的代码。**
   你"见过很多项目都这样"不等于这个项目也这样。没读到登录拦截器，就不能写"项目有登录拦截器"。

2. **严禁根据 pom.xml 判断某个技术一定被业务使用。**
   pom.xml 只能证明"引入了依赖"【已确认】，不能证明"业务在用"——starter 常被传递引入。结论"项目使用 Redis"必须找到 `RedisTemplate`/`StringRedisTemplate`/`Redisson` 等业务调用代码才能下；找不到就写"仅引入依赖，未发现业务调用"。

3. **严禁把 Redis 统一解释成"缓存"。**
   Redis 在不同项目里承担的职责完全不同（缓存/登录状态/分布式锁/排行榜/限流），必须按下方判定树从代码判断；判不出就写【无法从当前代码确定 Redis 在此处的具体用途】并列出可疑代码位置。

4. **严禁把 Sa-Token、Redis、MyBatis-Plus 的职责混为一谈。**
   典型错误："Sa-Token 用 Redis 存 Token"。除非代码或配置里能确认 Sa-Token 与 Redis 的集成（如 sa-token-redis 依赖 + 对应配置类/yml），否则二者关系是【待确认】。

5. **严禁为了完整而虚构接口。**
   只分析真实存在的 `@RequestMapping`/`@GetMapping`/`@PostMapping` 等注解方法。扫到几个写几个。

6. **严禁为了生成面试题而虚构项目行为。**
   每道面试题的题干和参考答案都必须能落到具体代码上；项目里没有的功能（秒杀、分库分表……）不出题。

## 每个结论必须尽量关联

- 文件路径：如 `src/main/java/com/xxx/controller/UserController.java`
- 类名、方法名
- 配置项：如 `application.yml` 中的 `spring.data.redis.host`
- 调用关系：A 调 B，依据是什么（方法调用语句）
- 数据库表：从 mapper XML / `@TableName` / SQL 推断
- API 路径：类级 `@RequestMapping` + 方法级 `@PostMapping` 拼接

给不出关联的结论，降级为【推测】或直接删掉。

## Redis 用途判定树

发现 Redis 相关代码后，按以下特征从代码判断用途，禁止跳过判断直接写"缓存"：

| 代码特征 | 用途 | 解释方向 |
|---|---|---|
| `opsForValue().set(key, …, TTL)`，且"先查 Redis、未命中再查库、回写" | 缓存 | 降低数据库读取压力 |
| sa-token-redis / spring-session 集成、key 含 `token`/`session`/`login:` 前缀 | 登录状态存储 | 分布式环境下维持会话 |
| `setIfAbsent` / `tryLock` / Redisson 锁 | 分布式锁 | 并发控制，防重复提交/超卖 |
| `opsForZSet()` + score 排序 | 排行榜 | 高频读取与排序 |
| 计数器 + TTL + 阈值判断 | 限流 | 访问控制 |
| 无法归类 | — | 写【无法从当前代码确定】，列出可疑代码位置 |

## 业务代码 vs 框架行为

- **业务代码**：项目作者写的类与方法，逐一分析其逻辑。
- **框架行为**：框架自动完成的部分。常见有：Spring Boot 自动配置（如 DataSource 自动装配）、MyBatis-Plus `BaseMapper` 内置 CRUD（无对应 XML）、依赖注入、AOP 代理、参数校验注解处理。
- 遇到"代码里没写但行为存在"的情况，明确标注【框架行为】并说明机制来源。
  示例："调用 `userMapper.selectById(id)` 无对应 XML——这是 MyBatis-Plus BaseMapper 的内置方法【框架行为】。"

## 表述对照示例

❌ 错误："项目使用 Redis 保存登录 Token，实现分布式会话。"

✅ 正确："项目引入 sa-token-redis 依赖【已确认：pom.xml】并配置了 Redis 连接【已确认：application.yml】，据此推断 Sa-Token 的 Token 持久化使用 Redis【推测】；未发现业务代码直接调用 RedisTemplate【已确认：全局搜索无结果】。"

❌ 错误："UserController：用户控制器。"（零信息量的废话）

✅ 正确："UserController 提供 5 个接口（见下表），对应'用户'模块，是本项目中接口最多的 Controller。"

❌ 错误（面试题）："Q：你们的秒杀是怎么防止超卖的？"（项目里根本没有秒杀）

✅ 正确："Q：本项目登录接口的完整调用链是什么？校验密码通过后为什么要调 `StpUtil.login()`？"

## 标记的呈现方式

- 正文内：`Sa-Token 负责登录认证【已确认：UserController.java login()】`
- 整段推断：段落末尾标 `【推测，依据：…】`
- 【待确认】必须带线索："需检查 SaTokenConfig 是否配置了 Redis 集成"
- 分析收尾时把所有【待确认】项汇总成清单，作为下一步排查任务

可视化看板中的所有文字同样适用本规则：四类标记写在 DATA 数据里，渲染时自动显示为彩色徽章（已确认=绿、推测=橙、框架行为=蓝、待确认=红）。标记写法必须保持【标记名：内容】格式才能被正确渲染。
